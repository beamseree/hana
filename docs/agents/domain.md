# Domain documents

This project has a single domain context.

Before implementation or architecture work, read:

1. `GLOSSARY.md` for the shared vocabulary.
2. `docs/product-spec.md` for the authoritative accepted experience.
3. The relevant sections of `docs/technical-design.md` and relevant ADRs in `docs/adr/`.
4. Linked prototype evidence when the change depends on native behavior.

Use glossary terms in specs, tickets, code and tests. Surface conflicts with accepted requirements or ADRs rather than silently changing them. A proposed ADR remains a proposal; an accepted requirement is not proof that an implementation works.

Record documented capabilities, automated checks and interactive observations separately. Preserve explicitly deferred tests and evidence limitations when turning prototype results into implementation work.
