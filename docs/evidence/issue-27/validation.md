## Decisions and limitations

- **No record revision on reorder.** The parent spec asks mutations to check "expected record/list revisions". Reorder checks the generation and the whole list (`expectedOrder`) inside the serialized write, but not the moved task's revision. Every concurrent change to the list's membership or order fails it. A concurrent title edit does not, because it changes neither. This is a deliberate reading of "record/list"; it needs explicit sign-off.
- There is no stored list revision, so the version 1 schema is unchanged. The precondition is the caller's full view of the list, which grows with the list. That is acceptable for personal Inbox/Today sizes.
- Renumbering changes other tasks' order keys without changing their revision or updated time, as in #26. Export and snapshot comparisons should compare whole records, not assume that the same revision means the same record.
- When the task itself was archived or completed concurrently, the error is `archivedTask` or `completedTask` rather than `staleList`. Either way nothing changes.
- Renumbering is dense (0, 1, 2…), so after it a move between neighbours renumbers again. It is correct, and costs one write per task in the list.
- Export (#28), snapshots (#29), capture UI and organizer UI are not implemented.
- This is process-crash and restart evidence only, not power-loss evidence, as in #24.
